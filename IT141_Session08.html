LAN Security Concepts: Someone on the Inside

Seven sessions of building, and the network works. Every port answers, every switch forwards, every host gets an address. That's the problem. A switch trusts whatever is plugged into it: it learns any MAC address, and it forwards any DHCP offer and any ARP reply to hosts that believe them. This session walks through how an attacker with one cable and one free wall jack turns that trust against the network, and names the defence for each. Session 9 builds them.

Module group exam

Modules 7–9: cross-module review

The exam covers DHCPv4, SLAAC and DHCPv6, and FHRP. If you can answer these cold, Sessions 6 and 7 have landed.

  • DHCPv4 server: exclusions first, then a pool per subnet with network, default-router (the client's gateway, not the server) and dns-server. A 169.254 address means no offer came back (Session 6).
  • Relay: ip helper-address on the interface where the clients' broadcasts arrive; the server picks the pool from the giaddr and needs a route back to it (Session 6).
  • RA flags: A=1 SLAAC; O=1 other settings from a stateless DHCPv6 server; M=1 address from a stateful one, with no-autoconfig for A=0. The IPv6 gateway always comes from the RA (Session 7).
  • DHCPv6: stateful is SOLICIT, ADVERTISE, REQUEST, REPLY; stateless needs only INFORMATION-REQUEST and REPLY. Clients send to UDP 547, servers to 546. A stateless server keeps no bindings (Session 7).
  • HSRP: a virtual IP and MAC shared by an active and a standby router. Highest priority wins (default 100), then the highest IP; standby preempt lets a higher-priority router take the role back. Hello 3 s, hold 10 s (Session 7).

Module 10.1

Endpoint security

Most attacks that make the news fall into a few kinds, and most of them reach the network through an endpoint: a laptop, desktop, server or IP phone, including the ones employees bring from home.

AttackWhat it does
DDoS (distributed denial of service)Many compromised devices, called zombies, flood a target at once, to slow or stop public access to it
Data breachServers or hosts are broken into to steal confidential information
MalwareMalicious software infects hosts. Ransomware, such as WannaCry, encrypts a host's data and demands payment to unlock it.

Devices at the edge

DeviceJob
VPN-enabled routerA secure connection for remote users across a public network. VPN can also be built into the firewall.
NGFW (next-generation firewall)Stateful inspection plus application control, a next-generation IPS (NGIPS), advanced malware protection (AMP) and URL filtering
NAC (network access control)AAA services and access policies for every kind of user and device. Cisco's ISE (Identity Services Engine) is one.

Protecting the endpoints themselves

Endpoints traditionally run their own protection: antivirus and antimalware, a host-based firewall, and a HIPS (host-based intrusion prevention system). Today they're best protected by a combination: NAC, AMP software on each host, and two appliances that watch the two ways most malware arrives.

ApplianceWatchesDoes
ESA (Email Security Appliance)Email (SMTP)Blocks known threats, discards email with bad links, catches malware that slipped through, encrypts outgoing mail. It pulls fresh threat data from Cisco Talos every few minutes.
WSA (Web Security Appliance)Web trafficURL filtering and blocklists, malware scanning, application control (allow, limit or block chat, video and so on), and decrypting web traffic to inspect it

Module 10.2

Access control: AAA and 802.1X

Two questions: who may log in to a network device, and who may plug a device into the network?

CCNA 1 callback In CCNA 1, AAA was a concept, with configuring it against a RADIUS or TACACS+ server left for later courses. In this course it stays a concept, but now you can see where the SSH login you've used since Session 1 fits into it.

Logging in to a device

The simplest method is a password on the console and vty lines. SSH is better: it needs a username and a password, and the session is encrypted. HQ's switches and R1 check those against a local database of usernames on each device:

S1 · the local user database SSH has used since Session 1
S1# show running-config | include username username admin secret 5 $1$mERr$hx5rVt7rPNoS4wqbXKX7m0 S1# show running-config | section line line con 0 password 7 0822455D0A16544541 login line vty 0 4 login local transport input ssh line vty 5 15 login local transport input ssh
  • Two kinds of login side by side. The console's login checks the line's own password: no username, and anyone who knows it gets in. The vty lines' login local checks the local user database: a username and a secret. SSH needs that, because an SSH login always has a username.
  • The limits of local authentication: the account exists separately on every device, so a password change means touching every box; and plain login local has no fallback, no second method to try.
  • The secret is stored as a hash (5 is an MD5-based type), so the password itself never appears. The hash here is made up.

AAA

AAA is the framework for controlling access to a device or a network:

AQuestionWhat it does
AuthenticationWho are you?Checks a username and password (or certificate) before letting anyone in
AuthorizationWhat may you do?Decides, automatically after login, which commands or services the user is allowed
AccountingWhat did you do?Logs usage: start and stop times, commands typed, bytes sent. Used for auditing, billing and troubleshooting, and as evidence.
Local AAAServer-based AAA
Where the accounts liveOn each router and switchOn one central AAA server
How the device asksIt checks its own listRADIUS or TACACS+
SuitsA small networkMany routers and switches: one place to add, change or remove a user

802.1X: who may plug in

IEEE 802.1X is port-based access control. A switch port (or a wireless access point) lets only authentication messages through (plus a few control protocols such as CDP and STP) until the device on it has proved who it is. Three roles:

RoleWhoJob
Supplicant (client)The PC or phone, running 802.1X client softwareProves its identity
AuthenticatorThe switch, or a wireless access pointThe go-between: passes the client's credentials to the server, and opens the port only if the server says yes
Authentication serverUsually a RADIUS serverDecides whether the client is allowed on

Had F0/5 in the Surveyor's printout run 802.1X, a stranger's laptop would have got nothing through it except the login exchange.

Module 10.3

Layer 2: the weak link

Firewalls, VPNs and intrusion prevention guard Layer 3 and up. But every layer sits on Layer 2: an attacker who can read or redirect frames on the LAN makes the security above it useless. And LANs were built on trust, back when everyone plugged into them worked for the company.

CategoryAttacksMitigationConfigured in
MAC tableMAC address floodingPort securitySession 9
VLANVLAN hopping, double-taggingTrunk guidelines: access ports never trunk, no DTP, an unused native VLANSession 2, already
DHCPDHCP starvation, DHCP spoofingDHCP snooping (and port security for starvation)Session 9
ARPARP spoofing, ARP poisoningDynamic ARP Inspection (DAI)Session 9
Address spoofingMAC and IP address spoofingIP Source Guard (IPSG)Named only
STPSTP manipulationBPDU Guard on access portsSession 9
ReconnaissanceCDP (and LLDP) reconnaissanceCDP off on edge ports (LLDP is already off by default)Session 9

None of that works if the switches themselves are easy to take over. Protect management too:

  • Secure management protocols: SSH, SCP, SFTP and TLS, never Telnet, TFTP, FTP or HTTP.
  • Out-of-band management: a separate network just for managing devices.
  • A dedicated management VLAN with nothing else in it. HQ has had one since Session 2: VLAN 99.
  • ACLs to filter who can reach the devices at all (CCNA 3 material).

Module 10.4

MAC address table flooding

A switch learns each frame's source MAC and the port it came in on. That table lives in memory, and it has a fixed size.

S1 · the MAC table on a normal day
S1# show mac address-table dynamic Mac Address Table ------------------------------------------- Vlan Mac Address Type Ports ---- ----------- -------- ----- 10 0060.5c3b.a801 DYNAMIC Fa0/1 10 00d0.97cc.00c1 DYNAMIC Po2 10 00e0.f70c.0011 DYNAMIC Po2 30 0090.2b5d.0030 DYNAMIC Po2 30 00d0.97cc.00c1 DYNAMIC Po2 99 0002.16aa.0012 DYNAMIC Po2 99 00d0.97cc.00c1 DYNAMIC Po2
  • A handful of entries: three PCs, D1's SVIs and S2's management SVI. The MAC addresses on this page are made up.
  • PC-C, PC-D and S2 are learned on Po2, not Po1. S2's end of Po1 is blocking (Sessions 4–5), so frames from S2's side reach S1 through D1. The MAC table shows the STP path.
  • D1 appears once per VLAN: one MAC for all its SVIs, but the table is keyed by VLAN plus MAC.
  • Capacity: a 2960's table holds about 8,000 addresses. NetAcad's example, a Catalyst 6500, holds 132,000. Either way, it fills in seconds against a tool sending thousands of frames a second. Entries age out after 300 seconds of silence.

A MAC address flooding attack fills the table on purpose. A tool such as macof sends thousands of frames a second, each from a made-up source MAC. The table fills in seconds. Once it's full, the switch can't learn any new address, so frames for a host it doesn't know become unknown unicasts, and the switch floods them out every port in the VLAN, including the attacker's. For those frames, the switch has turned into a hub.

Illustration Illustration: what an attack would look like. Packet Tracer doesn't run it.
S1 · during a MAC flooding attack from F0/5
S1# show mac address-table count Mac Entries for Vlan 10: --------------------------- Dynamic Address Count : ... Static Address Count : 0 Total Mac Addresses : ... ... Total Mac Address Space Available: 0 S1# show mac address-table dynamic vlan 10 Mac Address Table ------------------------------------------- Vlan Mac Address Type Ports ---- ----------- -------- ----- 10 0060.5c3b.a801 DYNAMIC Fa0/1 10 0a3f.1c77.e201 DYNAMIC Fa0/5 10 2e91.04b8.5d3c DYNAMIC Fa0/5 10 4a1c.9e02.77d3 DYNAMIC Fa0/5 10 6c08.f3a1.0b9e DYNAMIC Fa0/5 10 8e55.2d19.c460 DYNAMIC Fa0/5 ...
  • The tell: thousands of addresses on one access port, none of them real devices, and no space left. F0/5 is an unused port, but it's live in VLAN 10.
  • A full table doesn't throw out what it already knows. PC-A is still listed, and frames to it are still forwarded normally. But a quiet host's entry ages out after 300 seconds and can't be learned again while the table is full; from then on, its frames flood. Attack tools keep sending for exactly that reason.
  • The flood stays inside each VLAN. The full table stops S1 learning in every VLAN, but the attacker in VLAN 10 only sees VLAN 10's floods.
  • The neighbours fill up too. The bogus frames themselves go to unknown destinations, so S1 floods them up its trunks, and D1 and S2 learn the bogus addresses as well. One port, three full tables.
  • NetAcad also calls this a MAC address table overflow attack. The mitigation is port security: a limit on how many MAC addresses a port may learn. Session 9.

Module 10.5

VLAN attacks

Both VLAN attacks aim to get frames into a VLAN the attacker isn't in, without going through a router.

VLAN hopping

The attacker's host pretends to be a switch. It speaks DTP to the switch port, and if the port is willing, the two form a trunk. Now the attacker sends and receives on every VLAN the trunk carries.

Session 2 callback This is "Will it trunk?" with a laptop on one end. A port left in dynamic auto trunks with anything that asks in desirable mode.
S2 · PC-D's port: a static access port that won't negotiate
S2# show interfaces f0/11 switchport Name: Fa0/11 Switchport: Enabled Administrative Mode: static access Operational Mode: static access Administrative Trunking Encapsulation: dot1q Operational Trunking Encapsulation: native Negotiation of Trunking: Off Access Mode VLAN: 30 (LOGISTICS) Trunking Native Mode VLAN: 1 (default) Voice VLAN: none ...
S1 · Po1: a trunk built by hand
S1# show interfaces po1 switchport Name: Po1 Switchport: Enabled Administrative Mode: trunk Operational Mode: trunk Administrative Trunking Encapsulation: dot1q Operational Trunking Encapsulation: dot1q Negotiation of Trunking: Off Access Mode VLAN: 1 (default) Trunking Native Mode VLAN: 900 (NATIVE) ... Trunking VLANs Enabled: 10,30,99,900 ...
  • PC-D's port is static access, with negotiation off. A device on F0/11 can send all the DTP it likes; the port stays an access port in VLAN 30.
  • Po1 is a trunk because it was told to be one, and it sends no DTP (nonegotiate). Po2 and Po3 are the same.
  • Access Mode VLAN: 1 on a trunk is normal: that setting is only used if the port were an access port.

Compare a desk port on a 2960 nobody has configured, after a laptop plugged into it sends DTP in desirable mode:

  • The tell is The Native's tell from Session 2: administrative dynamic auto, operational trunk, on a port nobody configured as a trunk.
  • What the laptop now has: a trunk carrying every VLAN on the switch. It can tag frames into any of them, with no router involved.
  • On a 2960, a port nobody has configured is in dynamic auto, so it trunks if the far end asks. Other Cisco switches have different defaults, so check before trusting one.
  • Why it can't happen at HQ: every port on S1, S2 and D1 is a static access port, a static trunk with nonegotiate, a routed port (D1's link to R1), or parked. None is dynamic.

Double-tagging

The second VLAN attack needs a stranger set-up, so here it is on paper, on a version of HQ that doesn't exist: suppose one of S1's access ports were in VLAN 900, the native VLAN.

  • It's one-way. PC-D's reply goes to the intruder's MAC in VLAN 30, and the intruder is in VLAN 900. Nothing retags it, and VLAN 900 has no gateway. The intruder can send frames in, but gets nothing back.
  • It can't happen at HQ, because step 1 needs an access port in VLAN 900, and VLAN 900 has none. That's Session 2's design paying off: the native VLAN is used only on trunks.
  • For the curious (beyond this course): real switches can also tag the native VLAN (vlan dot1q tag native), so step 2 never strips anything.

NetAcad's three guidelines stop both VLAN attacks, and HQ has followed all three since Session 2:

  • Turn trunking off on every access port: switchport mode access.
  • Turn auto-trunking off on trunk links, so trunks are only ever made on purpose: switchport mode trunk with switchport nonegotiate.
  • Use the native VLAN only on trunks: VLAN 900 has no access ports and no hosts.

Module 10.5

DHCP attacks

DHCP hands out the most important settings a host has (its address, gateway and DNS server) to anyone who asks, from anyone who answers. Both attacks are stopped by DHCP snooping.

AttackHowThe damage
DHCP starvationA tool such as Gobbler sends DHCPDISCOVERs from thousands of made-up MAC addresses until every address in the pool is leasedDenial of service: real clients get no address. It's often the first step of a spoofing attack.
DHCP spoofingA rogue DHCP server on the LAN answers clients before, or instead of, the real oneWhatever it hands out: a wrong gateway (the attacker's own host, a man-in-the-middle), a wrong DNS server (fake websites), or a wrong address (denial of service)
Session 6 callback Session 6 warned that the home router on S3 F0/3, plugged in by a LAN port instead of its internet port, would start answering the Shipping LAN's DHCP requests. That's DHCP spoofing, with no attacker at all: a rogue server can be an accident.
Illustration If the home router on S3 F0/3 were plugged in by a LAN port. A Packet Tracer copy of the network could show this one; the course network never did it.
PC-B · a lease from the home router's LAN side
C:\> ipconfig /all FastEthernet0 Connection:(default port) Connection-specific DNS Suffix..: ... Physical Address................: 0060.70AA.0020 Link-local IPv6 Address.........: FE80::260:70FF:FEAA:20 IPv6 Address....................: 2001:DB8:ACAD:20:260:70FF:FEAA:20 IPv4 Address....................: 192.168.0.100 Subnet Mask.....................: 255.255.255.0 Default Gateway.................: FE80::2 192.168.0.1 DHCP Servers....................: 192.168.0.1 DHCPv6 IAID.....................: DHCPv6 Client DUID..............: ... DNS Servers.....................: 2001:DB8:ACAD:20::100 ...
  • The tell: an address from a subnet that isn't Shipping's (192.168.0.x, not 192.168.20.x), and a DHCP server that isn't R2's 192.168.20.1.
  • Every IPv6 line is unchanged. The home router is an IPv4 DHCP server; PC-B's SLAAC address, gateway and IPv6 DNS server still come from R2. (A rogue IPv6 source would be a stray router sending RAs: Session 7's warning.)
  • The damage: PC-B's gateway is now the home router's LAN side, which can't reach SRV1 or HQ. That's NetAcad's "wrong default gateway". A malicious server would hand out its own address as the gateway and forward everything: a man-in-the-middle.
  • When the rogue wins: a client with a lease renews by unicast with its own server, so it keeps the good lease. The rogue only competes when a client sends a fresh DISCOVER (a new PC, a reboot, a release and renew), and the client takes the first offer that arrives. A server on the same switch usually answers first.
  • Starvation leaves its tell on the server: R2's show ip dhcp binding full of hardware addresses that match no real PC, and new clients falling back to 169.254.

Module 10.5

ARP spoofing and poisoning

ARP has no way to check who's telling the truth. A host broadcasts "who has 192.168.10.1?" and believes whatever reply comes back. It even accepts replies nobody asked for.

A reply nobody asked for is a gratuitous ARP. It has honest uses: in Session 3 a new SVI announced itself with one, and in Session 7's HSRP what-if, a new active router did the same. An attacker uses the same message to lie. It sends gratuitous ARPs saying "192.168.10.1 is at my MAC" (ARP spoofing), and the hosts' ARP caches are now poisoned. Every frame they send to their gateway goes to the attacker, who copies it and passes it on: a man-in-the-middle.

PC-C · the gateway's real MAC
C:\> arp -a Internet Address Physical Address Type 192.168.10.1 00d0.97cc.00c1 dynamic
Illustration Illustration: what an attack would look like. Packet Tracer doesn't run it.
PC-C · after ARP poisoning from S1 F0/5
C:\> arp -a Internet Address Physical Address Type 192.168.10.1 0040.0bad.0005 dynamic 192.168.10.102 0040.0bad.0005 dynamic
  • 192.168.10.1 is D1's Vlan10 SVI. (Session 7's virtual MAC belonged to the HSRP what-if; HQ doesn't run HSRP.)
  • After the attack, the gateway's IP maps to the intruder's MAC. PC-C still sends to 192.168.10.1, but every frame goes to the laptop on S1 F0/5, which reads it and passes it on to D1. PC-C notices nothing.
  • A common tell: two IP addresses with one MAC, the gateway and the intruder's own address. The second line only shows up if PC-C has talked to the intruder.
  • Both directions: a real man-in-the-middle also poisons D1, so the replies come through the laptop too.
  • The switch isn't fooled, and doesn't need to be. S1 learns the intruder's MAC on F0/5, where it really is. The MAC table is right; the hosts' ARP caches are wrong. That's what separates ARP poisoning from MAC address spoofing.

IPv6 replaces ARP with ICMPv6 Neighbor Discovery, which can be forged the same way; switches have separate features to protect it, beyond this course. On IPv4, the mitigation is Dynamic ARP Inspection (DAI), which Session 9 configures.

Module 10.5

Address spoofing

Using someone else's address.

  • IP address spoofing: the attacker takes another host's IP address, or a random one. Hard to catch inside the subnet the address belongs to.
  • MAC address spoofing: the attacker sets its MAC to the victim's. The switch moves the victim's MAC table entry to the attacker's port, and sends the victim's frames there. When the victim sends again, the switch moves the entry back, so the attacker keeps sending frames to hold it.
  • A switch has no way to check which port a MAC address really belongs on. IP Source Guard (IPSG) is the mitigation for both. NetAcad names it; this course doesn't configure it.

Module 10.5

STP manipulation

Spanning Tree elects the root bridge from whatever BPDUs it hears. It doesn't ask who sent them.

An attacker's host sends BPDUs announcing a lower bridge ID than D1's. The switches hold a new election and the attacker wins. With one cable, that mostly causes disruption: every change of topology costs a reconvergence and extra flooding. An attacker connected to two switches can do worse, and sit in the middle of the traffic between them. The mitigation is BPDU Guard on every access port: a port with nothing but hosts on it should never hear a BPDU, so if it does, the switch shuts it.

Session 4 callback Session 4 showed the PortFast and BPDU Guard commands as syntax, and said they'd be used in Session 9. This is the attack they're for.

Illustration Illustration: what an attack would look like. Packet Tracer doesn't run it.
S1 · a laptop on F0/5 claims to be the root
S1# show spanning-tree vlan 10 VLAN0010 Spanning tree enabled protocol rstp Root ID Priority 10 Address 0040.0BAD.0005 Cost 19 Port 5(FastEthernet0/5) Hello Time 2 sec Max Age 20 sec Forward Delay 15 sec Bridge ID Priority 28682 (priority 28672 sys-id-ext 10) Address 0060.47BB.0011 Hello Time 2 sec Max Age 20 sec Forward Delay 15 sec Aging Time 20 Interface Role Sts Cost Prio.Nbr Type ---------------- ---- --- --------- -------- -------------------------------- Fa0/1 Desg FWD 19 128.1 P2p Fa0/5 Root FWD 19 128.5 P2p Po1 Desg FWD 9 128.27 P2p Po2 Desg FWD 3 128.28 P2p
  • Priority 0, plus VLAN 10's extended system ID, is 10: lower than D1's 24586, so every switch in VLAN 10 accepts the laptop as root.
  • What moves: S1's root port moves from Po2 to F0/5, a desk port. D1, the old root, now reaches the root through Po2 (cost 3 + 19 = 22). S2 keeps Po3 as its root port (22 + 3 = 25, against 19 + 9 = 28 through Po1). The links between the switches barely change.
  • With one cable, the fake root mostly causes disruption: every topology change shortens MAC aging and causes extra flooding, and repeated changes make the network unstable. To sit in the middle of traffic, as NetAcad describes, the attacker would need to be connected to two switches. PC-A's traffic doesn't flow through F0/5 here.
  • The hole is a live access port that listens to BPDUs. BPDU Guard would shut F0/5 at the first BPDU, before any election.

Module 10.5

CDP reconnaissance

Before attacking, an attacker looks around. Cisco Discovery Protocol does a lot of the looking for them.

CDP is on by default on every Cisco device and every port. It announces the device's name, IP address, model, IOS version, capabilities and VLAN every 60 seconds, unencrypted and unauthenticated. Administrators use it to map and troubleshoot a network. So can anyone who captures one frame on an access port.

Here's what S1 knows about S2 from CDP. Every CDP-enabled port sends the same kind of advertisement, desk ports included. A laptop plugged into F0/5 would receive S1's every 60 seconds.

S1 · what one CDP frame tells anyone listening
S1# show cdp neighbors detail ------------------------- Device ID: S2 Entry address(es): IP address: 192.168.99.12 Platform: cisco WS-C2960-24TT-L, Capabilities: Switch IGMP Interface: FastEthernet0/23, Port ID (outgoing port): FastEthernet0/23 Holdtime : 171 sec Version : Cisco IOS Software, C2960 Software (C2960-LANBASEK9-M), Version 15.0(2)SE4, RELEASE SOFTWARE (fc1) Technical Support: http://www.cisco.com/techsupport Copyright (c) 1986-2013 by Cisco Systems, Inc. Compiled Wed 26-Jun-13 02:49 by prod_rel_team advertisement version: 2 VTP Management Domain: '' Native VLAN: 900 Duplex: full Management address(es): IP address: 192.168.99.12 ------------------------- Device ID: S2 ... Interface: FastEthernet0/24, Port ID (outgoing port): FastEthernet0/24 ...
  • Read it as an intruder would. The management IP (VLAN 99 has no hosts on purpose, and CDP hands its address to a stranger anyway). The exact model and IOS version, to look up known weaknesses. The VLAN: on a desk port this field carries the port's access VLAN; on a trunk, the native VLAN.
  • CDP isn't really a broadcast. It goes every 60 seconds to a multicast address, 01:00:0C:CC:CC:CC, that every Cisco device listens for. Switches flood it, so the effect is the same: anyone on the port can read it. Receivers keep it for a 180-second holdtime, which is why Holdtime counts down.
  • S2 appears twice, once per cable of Po1. CDP runs on each physical port, not on the port-channel: to STP the bundle is one link, to CDP it's two cables.

The fix is to stop advertising where strangers can listen. These are Module 10's commands. HQ doesn't change today; Session 9 turns CDP off on the desk ports along with everything else.

S1 · CDP and LLDP off (the commands, not applied at HQ today)
! Per port: stop CDP on the desk ports only (the trunks keep it) S1(config)# interface range f0/1 - 20 S1(config-if-range)# no cdp enable S1(config-if-range)# end S1# show cdp interface f0/5 S1# ! ! Globally: CDP off on every port of the switch S1# configure terminal S1(config)# no cdp run S1(config)# end S1# show cdp % CDP is not enabled ! ! LLDP, the IEEE standard equivalent S1# configure terminal S1(config)# interface range f0/1 - 20 S1(config-if-range)# no lldp transmit S1(config-if-range)# no lldp receive S1(config-if-range)# exit S1(config)# no lldp run
  • An empty show cdp interface f0/5 is the proof: the command only lists ports with CDP on. cdp enable and cdp run undo it.
  • Per port is the recommendation. no cdp run goes further, and costs things: the native VLAN mismatch warning from Session 2 comes from CDP; a Cisco IP phone learns its voice VLAN through CDP; and show cdp neighbors is a handy cabling check.
  • LLDP is the open-standard version of CDP, and it leaks the same kind of information. On Catalyst switches it's off by default, so no lldp run mostly makes sure. Per port, sending and listening are separate: it takes both lines to stop it.

CASE FILE D-06

The Impostor

Wears whatever badge the network will accept. Floods a switch with thousands of made-up MAC addresses until it can't learn real ones, and starts flooding their frames to every port in the VLAN. Answers DHCP requests before the real server can, handing out its own address as the gateway. Tells every host on the VLAN that the gateway's IP address now lives at its MAC. Claims to be the root bridge. It needs no password and forces no lock: it just uses the trust a switch gives to anything plugged into it.

Tell: one access port with hundreds of MAC addresses in show mac address-table; a gateway whose MAC changed in a PC's arp -a; a PC with a lease from an address range nobody configured; a root bridge in show spanning-tree that isn't D1.

See also: Attacks and their mitigations · Name that attack

Debrief The Impostor's tricks all start the same way. What does every one of them need, and why does HQ's design already stop VLAN hopping and double-tagging, but none of the others? (Each one needs a live port to plug into. VLAN hopping needs a port that will negotiate a trunk, and double-tagging needs an access port in the native VLAN. HQ has neither: every access port is static, and VLAN 900 has no access ports. The other attacks work through an ordinary access port, which is exactly what a desk jack is. Stopping them means the switch has to check what arrives on its access ports: Session 9.)

Watch for this

Common Module 10 mistakes

Most Module 10 mistakes are matching an attack to the wrong defence, or thinking a defence covers more than it does.

1 · VLAN hopping vs double-tagging

Two different attacks. Hopping forms a trunk with DTP and works both ways. Double-tagging hides a second tag behind the native VLAN and only goes one way.

2 · ARP poisoning vs MAC spoofing

ARP poisoning changes the hosts' ARP caches; the switch's MAC table stays right. MAC spoofing changes the switch's MAC table; the hosts' caches stay right. Ask which table is lying.

3 · DHCP starvation vs spoofing

Starvation empties the real server's pool (its tell is on the server). Spoofing adds a fake server (its tell is on the client). One often follows the other.

4 · Thinking MAC flooding reaches every VLAN

The flood stays inside each VLAN. An attacker in VLAN 10 sees VLAN 10's traffic, not VLAN 30's.

5 · One fix for every attack

Each mitigation has a target: port security for flooding, DHCP snooping for DHCP, DAI for ARP, IPSG for address spoofing, BPDU Guard for STP. DHCP starvation is the one with two: snooping and port security.

6 · Mixing up the 802.1X roles

The supplicant is the client, the authenticator is the switch or access point, and the authentication server (usually RADIUS) decides. The switch passes credentials along; it doesn't judge them.

7 · "Parked" doesn't mean "safe from everything"

Parking protects the ports nobody uses. The attacks on this page work just as well through a port somebody does use. Session 9 needs both: parking for the empty ports, port security and the rest for the live ones.

Recurring segment

The Ticket

Turn it into steps before you open the answer.

Ticket #141-08 · Priority: high · From: Front Desk

Since this morning, two PCs at the front desk can reach each other but not the internet or the file server. A third PC is fine. A visitor was using the spare desk by the window yesterday. We restarted everything and it didn't help.

One way to break it down
  1. Same subnet works, everything beyond it doesn't: the problem is the gateway, or what the PCs think the gateway is.
  2. "We restarted everything" means every PC sent a fresh DHCP discover. If a rogue server answered first, the restarted PCs have its settings. Check ipconfig /all: is the address 192.168.10.x, is the gateway 192.168.10.1, and is the DHCP server R1's 10.0.0.9? A lease from a server nobody configured is DHCP spoofing.
  3. If the settings are right, check arp -a: does 192.168.10.1 map to D1's real MAC, or to a MAC that also belongs to another address? That's ARP poisoning.
  4. Find the port: look up the rogue MAC in S1's and S2's show mac address-table. Expect the spare desk's jack, a live, unused port in VLAN 10.
  5. Tonight: shut that port, then renew the affected PCs (ipconfig /release and /renew, or arp -d for a poisoned cache).
  6. For good: park every unused port; DHCP snooping and DAI, with only the uplinks trusted. Session 9.

Applied

Worked examples

Think it through before you expand the answer.

Flooding

Could it see VLAN 30?

Suppose an attacker on S1 F0/5 (VLAN 10) filled S1's MAC table, and then captured frames sent to PC-C after PC-C had been quiet for a while. Could it also capture PC-D's traffic in VLAN 30?

Show answer

No. Once PC-C's entry aged out, S1 couldn't learn it again while the table was full, so frames for PC-C became unknown unicasts and were flooded out every port in VLAN 10, including F0/5. VLAN 30's traffic floods too, because S1 can't learn there either, but only out VLAN 30's ports. Flooding never crosses into another VLAN. To see it, the attacker would need a port in VLAN 30, or a trunk.

VLAN attacks

Why can't double-tagging work at HQ?

An attacker on a VLAN 10 port at HQ sends a frame with two 802.1Q tags: outer 10, inner 30. What happens?

Show answer

Nothing useful for the attacker. Double-tagging needs the attacker's access port to be in the trunk's native VLAN, so the first switch sends the frame across the trunk untagged and the hidden inner tag is the only one left. The attacker is in VLAN 10, and HQ's native VLAN is 900, which has no access ports at all. At most, the frame stays in VLAN 10 (many switches simply drop a tagged frame arriving on an access port). It can't reach VLAN 30.

DHCP

Starvation, then spoofing

Why would an attacker run DHCP starvation before plugging in a rogue DHCP server?

Show answer

With the real server's pool empty, the real server can't answer new clients, so the rogue server's offers are the only ones they get. Starvation alone is a denial of service; with spoofing after it, the attacker controls every new client's gateway and DNS server.

ARP

Who sees the poisoned entry?

An attacker in VLAN 30 sends gratuitous ARPs claiming 192.168.30.1. PC-C is in VLAN 10. Is PC-C's ARP cache poisoned?

Show answer

No. ARP is a broadcast, and broadcasts stay inside their VLAN. Only hosts in VLAN 30 hear the lie, and only they would send their gateway traffic to the attacker.

Mitigation

One attack, two answers

Port security and DHCP snooping both appear in NetAcad's list against DHCP starvation. Why does each one help?

Show answer

Starvation comes from one port pretending to be thousands of clients. Port security limits how many MAC addresses that port may use, so the switch drops the made-up ones. DHCP snooping can rate-limit DHCP messages on untrusted ports, so one port can't send thousands of requests a second. (It also checks that each request's client MAC matches the frame's source, but a tool that fakes both passes that check.)

CDP

Off everywhere?

A colleague suggests no cdp run on every switch at HQ. Why might that be too much?

Show answer

CDP is useful on links between Cisco devices: it warns about native VLAN mismatches and tells IP phones their voice VLAN. The risk is on edge ports, where users and attackers plug in. no cdp enable on the access ports closes the leak and keeps CDP where it helps.
